**两条重要结论：**

1. **只有 GPIO21 和 GPIO22 读到了高电平**（在禁用内部上拉的情况下），
   其余候选引脚都读到低。说明**确实有外部上拉电阻接在 21/22 上** ——

结合起来：**引脚是对的（就是 21/22），但芯片不应答。**

## 四、最可能的原因

### ⚠️ 更正声明（重要）

本文档早先版本把「**编码器 GND 没有和 ESP32 共地**」列为首选嫌疑，
依据是「两条线都读到高电平 → 上拉在、芯片却不应答」。

**那个依据是错的。**「两线都读到高」是**引脚悬空时的假读数**。
改用「内部下拉 + 读电平」重测后结论反转（见第四节之二）。
因此 GND 假设**失去主要证据支撑** —— 它没有被推翻，但不再是首选。

### 已排除：编码器没供电（用户确认 VCC 接在 ESP32 的 3.3V）

ESP32 由 USB 供电，所以 3.3V 是有的 →「编码器完全没电」基本排除。

### 第二次更正：测试方法又修了一处，数据如下（当前为止最可信）

上一版把 `G` 的结论当成"已证实"，**这一步下得太早**。修正后连续做了三轮测量：

**第 1 轮 — 修掉 `Wire.end()` 缺失**（引脚还挂在 I2C 外设上时 `pinMode()` 不可靠）：

```
GPIO22 -> 拉低后能自己回到高, 有外部上拉
共 1 个引脚有外部上拉
```

**第 2 轮 — 改成测上升时间**（能区分"没有上拉"和"弱上拉"）：

```
GPIO22  上升=1us  内部下拉后=高(强上拉)
（GPIO21 没有任何输出 —— 拉低后 3ms 内不回升）
```

**第 3 轮 — 连续监视，同时打印"自由电平"和"内部下拉后的电平"**：

```
监视: SDA 自由=1 下拉后=0 | SCL 自由=1 下拉后=1 | 器件数=0
```

### 三轮数据合起来说明什么

| 线 | 自由电平 | 45k 内部下拉后 | 拉低后 3ms 内回升 | 判读 |
|---|---|---|---|---|
| **SCL (GPIO22)** | 1 | **1** | **1 µs** | 有**强**上拉（4.7k 级），完全正常 |
| **SDA (GPIO21)** | 1 | **0** | **不回升** | 没有可测到的上拉；"自由=1"更像**悬空脚残留电荷** |

关键推理：如果 GPIO21 上真有一个哪怕很弱的上拉（100k 级），
拉低后放开应该在几十 µs 内回升 —— 3ms 的窗口足够测到 10MΩ 级。
它**完全不回升**，且 45k 内部下拉就能把它摁到低 → 指向"**没有上拉 / 悬空**"。

### ⚠️ 但用户万用表实测两条线分别是 3.6V 和 3.3V

这与上面的结论**直接冲突**，而且我**无法远程判定谁对**。两种测量测的本该是同一件事，
所以最可能的解释是**两边测的不是同一个点**（例如万用表测的是编码器模块那一端，
而我的固件测的是 ESP32 这一端）。若如此，恰好说明**两端之间那根 SDA 线是断的**。

**这件事没查清之前，不再下"线断了"的结论。**

### 🔴 3.6V 这个读数本身是个独立风险，值得单独处理

- ESP32 的 GPIO **绝对最大额定就是 3.6V**。I2C 空闲电平出现 3.6V，
  说明那条线上很可能存在**上拉到 5V** 的路径。
- 这与 guide 第 2 节的警告完全对上：
  > 编码器曾出现"实物丝印接 5V"和"厂家图接 3.3V、5V 时去掉 R3"的冲突。
  > ESP32 的 SDA/SCL 侧信号应为 3.3V 电平；**5V 上拉需要适当的 I²C 双向电平转换或按厂家资料修改模块**。
- 也就是说：即使通信问题解决了，**3.6V 长期挂在 ESP32 引脚上本身就是超规使用**，
  应当按厂家资料处理（改 3.3V 上拉 / 按说明去掉 R3 / 加电平转换）。

**在搞清 3.6V 来自哪里之前，建议不要长时间通电。**

### 需要你回复的两件事

1. **3.6V 和 3.3V 分别是哪个引脚？**（GPIO21 还是 GPIO22）
2. **是在哪里量的？** ESP32 排针这一端，还是编码器模块那一端？

### 最省事的决定性测法：断电测通断

把电断掉，用万用表**电阻/通断档**，直接量这几个"两端之间"是否导通（应接近 0Ω）：

| 量这一端 | 到那一端 |
|---|---|
| ESP32 的 GPIO21 排针 | 编码器模块的 SDA 引脚 |
| ESP32 的 GPIO22 排针 | 编码器模块的 SCL 引脚 |
| ESP32 的 GND 排针 | 编码器模块的 GND 引脚 |
| ESP32 的 3.3V 排针 | 编码器模块的 VCC 引脚 |

这一组测量**不依赖任何解释**，直接回答"线到底通不通"，能一次性结束这场分歧。

### 附：为什么"缺 GND"不会让上拉消失（这条推理本身仍然成立）

不管上面那场分歧最后怎么收场，有一条推理是站得住的 ——
**模块缺 GND 不会导致它的上拉电阻测不到**：

```
ESP32 3.3V ──► 模块 VCC ──► 上拉电阻 4.7k ──► 模块 SDA ──► ESP32 GPIO21
                                                              │
                              ESP32 GPIO21 内部下拉 45k ◄─────┘
                                                              │
                                                        ESP32 GND ──► 回到 3.3V
```

上拉的电流回路**完全在 ESP32 内部闭合，不经过模块的 GND**。
所以：**如果那条数据线是通的，无论模块 GND 接没接，上拉都会被测到。**

这条推理的价值在于：它把"SDA 是否连通"和"GND 是否共地"**解耦**成两个独立问题，
可以分别验证、不必纠缠。但它**不能**用来断定线断了 ——
那需要上面的通断实测来定论。

### 单是 SDA 断线就能完整解释全部现象

| 现象 | 解释 |
|---|---|
| `NACK=112`、`超时=0` | 主机发完地址后释放 SDA 等 ACK，没人应答 → 干净 NACK |
| 一个器件都找不到 | 从机靠**拉低 SDA** 应答 ACK，SDA 断了就永远没有 ACK |
| 不超时、低速 10kHz 也不行 | SCL 正常（GPIO22 有上拉），时钟跑得完，纯物理断线 |

巧合但值得注意：**没上拉的正好是 GPIO21 = SDA**，而 SDA 正是 ACK 用的那根线。

### 仍未排除的独立故障

GND 是否共地**无法远程测量**，要用万用表。它与 SDA 断线是**两个可能并存的故障**：

- 即使 GND 真的没接，修好 SDA 线后仍然不会工作
- 所以顺序应是：**先修 SDA 线 → 再查 GND**

## 四之二、决定性测试：GPIO 上拉扫描（`G` 命令）

`G` 会逐个引脚：**启用 ESP32 内部下拉（约 45k）后再读电平**。
若仍读到高，说明该引脚上挂着一个比内部下拉强得多的**外部上拉电阻**。

> 方法学要点：必须在**启用内部下拉**的条件下读。
> 只用 `pinMode(INPUT)` 读悬空脚会得到随机假高电平 —— 早先那次误判就是这么来的。

```
=== 扫描外部上拉电阻 ===
  GPIO22  -> 读到高, 有外部上拉
  共 1 个引脚有外部上拉
  -> 只有 1 个引脚有上拉, 而 I2C 需要 2 根线。
     说明 SDA 和 SCL 里有一根断了 / 没接上。
     有上拉的是 GPIO22
```

AS5600 模块在 SDA 和 SCL 上各有一个上拉电阻，正常应当是 **2 个引脚有上拉**。
现在只有 1 个 → **两根数据线里有一根不通，且不通的是 GPIO21（SDA）**。

### 附带确认：不是速率/上拉强度问题（`L` 命令）

`L` 在 50kHz 与 10kHz 下并联内部上拉重试，排除"上拉太弱导致上升沿回不去"：

```
50 kHz: 0x36 无应答, 总线上也没有任何器件
10 kHz: 0x36 无应答, 总线上也没有任何器件
结论: 低速也不行 -> 问题不在速率/上拉强度
```

## 四之三、连续监视模式（`W`，用来抓接触不良）

固件命令 **`W`**：进入后**每秒扫一次总线**并打印空闲电平和器件数，
方便一边轻轻晃动 / 重插线，一边看结果有没有变化。

```
>> 进入连续监视模式 (每秒一次)
  监视: 空闲 SDA=1 SCL=1  器件数=0
  ...
```

一旦扫到 0x36，立刻打印 `*** 找到 AS5600! 接线通了 ***` 并**自动切换到读数模式**。

```powershell
python host\serial_watch.py --port COM9 --seconds 60 --no-reset --send W --send-after 1
```

## 五、接下来要做的检查（按优先级）

### 优先级 1：修好 GPIO21（SDA）那根线

拔下重插，或换一根杜邦线。修完重跑 `G`：

```powershell
python host\serial_watch.py --port COM9 --seconds 10 --no-reset --send G --send-after 1
```

**通过判据：`共 2 个引脚有外部上拉`（21 和 22 都有）。**

### 优先级 2：确认 GND（仍然要做，但排在后面）

| # | 检查项 | 期望 / 判断方法 |
|---|---|---|
| 1 | **编码器 GND 是否真的接到 ESP32 的 GND** | 万用表通断档量两端，应导通 |
| 2 | 编码器模块上 VCC 焊盘 ↔ GND 焊盘 的电压 | 应约 **3.3V**；0V 或飘忽 → 供电/地有问题 |
| 3 | 编码器模块上的电源指示灯亮不亮 | 应当亮 |
| 4 | 万用表量 ESP32 的 **GPIO21 排针 ↔ GND** | 应约 3.3V；读到 ~0V 或飘 → 就是这根断了 |
| 5 | DuPont 线本身是否导通 | 杜邦线断芯很常见 |

> 原理：编码器模块的上拉电阻会把两根数据线都拉到 3.3V。
> 悬空/断线的脚直接用万用表量会读到接近 0V 或不稳定。

### 关于「要不要接电池」

- **不要**为了让编码器有电而接电池 —— 你已确认 VCC 取自 ESP32 3.3V，
  编码器供电与驱动功率无关。
- 驱动板功率继续保持断开，这是最安全的状态。
